# PhoneMic Protocol v1 — спецификация

Этот документ — **единственный источник истины** для обеих сторон (Android-приложение и Windows-приложение).
Любая реализация обязана точно следовать константам, структурам пакетов и схемам JSON из этого файла.

## 1. Обзор и роли

PhoneMic превращает телефон Android в микрофон для Windows 11. Звук захватывается на телефоне,
передаётся по выбранному транспорту и подаётся в виртуальный микрофон-драйвер Windows
(`PhoneMic Virtual Microphone`), который видят Zoom/Discord/OBS и любые другие приложения.

| Компонент | Роль |
|---|---|
| **Телефон (Android)** | Клиент управления + источник звука. Всегда сам инициирует TCP/UDP-подключения к ПК. |
| **ПК (Windows)** | Сервер управления (TCP+TLS) + приёмник звука. Декодирует и подаёт PCM в драйвер. |
| **Исключение — Bluetooth** | ПК является **клиентом** и подключается к RFCOMM-службам телефона (телефон — сервер, слушает 2 канала). Протокол поверх — тот же. |

## 2. Константы

| Константа | Значение |
|---|---|
| `PROTO_VERSION` | `1` |
| `DISCOVERY_PORT` (UDP) | `47820` |
| `CONTROL_PORT` (TCP, настраиваемый в UI обеих сторон) | `47821` |
| `MEDIA_PORT` (UDP или TCP) | `47822` |
| `MEDIA_MAGIC` | `0x504D` (ASCII «PM», big-endian в пакете) |
| Имя/префикс для discovery и Wi-Fi Direct | `PhoneMic` |
| RFCOMM UUID канала управления | `B2C4D6E8-F0A2-4C6E-8A0C-2E4A6C8E0B12` |
| RFCOMM UUID медиа-канала | `B2C4D6E8-F0A2-4C6E-8A0C-2E4A6C8E0B13` |
| Формат аудио (внутренний, фиксированный) | PCM 16-bit LE, mono, 48000 Гц |
| Максимальный размер control-сообщения | 65536 байт |

## 3. Транспорты и режимы медиа

| Транспорт | Control-канал | Медиа-канал | Примечания |
|---|---|---|---|
| **Wi-Fi (LAN)** | TCP+TLS на `CONTROL_PORT` ПК | UDP на `MEDIA_PORT` ПК (или TCP+TLS — настраивается) | Обычная домашняя сеть. Discovery по UDP-broadcast. |
| **USB (tethering)** | То же, что Wi-Fi, адрес ПК = шлюз USB-сети | То же | Android 14+ использует NCM, Windows 11 поддерживает его нативно. Телефон определяет шлюз интерфейса `usb*/rndis*` и подключается к нему. |
| **USB (adb reverse)** | TCP+TLS на `127.0.0.1:47821` телефона (туннель на ПК) | TCP+TLS на `127.0.0.1:47822` | ПК выполняет `adb reverse tcp:47821 tcp:47821` и `adb reverse tcp:47822 tcp:47822`. Если адрес клиента для сервера — loopback, сервер обязан выбрать `media_mode=tcp`. |
| **Wi-Fi Direct** | Как Wi-Fi | UDP (предпочтительно) | ПК = Group Owner (`WiFiDirectAdvertisementPublisher`), телефон подключается через `WifiP2pManager`, адрес ПК = `groupOwnerAddress`. WPA2-пароль публикуется в UI ПК. |
| **Bluetooth (RFCOMM)** | RFCOMM `...0B12`, фрейминг AES-GCM (см. §8.4) | RFCOMM `...0B13`, фрейминг как TCP | Сопряжение стандартное (настройки Windows ↔ Android). По BT разрешён только Opus, битрейт ≤ 64 kbps. |

Режим медиа (`media_mode`) решает **сервер** в сообщении `ok`: `udp` или `tcp`.
Клиент может предложить режим в `start_stream`, но финальное слово за сервером.

## 4. Discovery (UDP broadcast, порт 47820)

Телефон широковещательно рассылает (255.255.255.255 и directed broadcast каждой подсети):
```json
{"t":"discover","proto":1,"device":"Pixel 8"}
```
ПК отвечает юникастом на адрес отправителя:
```json
{"t":"announce","proto":1,"name":"DESKTOP-ABC","port":47821,
 "cert_fp":"a1b2...f0","transports":["wifi","usb","wfd"]}
```
`cert_fp` — SHA-256 отпечаток TLS-сертификата сервера (hex, lowercase, без разделителей). Используется для предзаполнения пина в UI телефона.

## 5. Control-канал (TCP+TLS)

1. TCP-подключение к `CONTROL_PORT`, затем TLS-рукопожатие.
   - Сертификат сервера: самоподписанный RSA-3072, CN=`PhoneMic-<имя ПК>`, генерируется при первом запуске.
   - Проверка сертификата клиентом: **pinning по отпечатку SHA-256** (см. §9). При первом подключении (TOFU) отпечаток показывается пользователю для подтверждения.
2. Поверх TLS — фрейминг: `4 байта big-endian длина` + `UTF-8 JSON`. Порядок байт длины — network byte order.

### 5.1 Последовательность handshake

```
C -> S  {"t":"hello","proto":1,"app":"PhoneMic-Android","app_ver":"1.0.0",
         "device":"Pixel 8","android":"16",
         "transports":["wifi","usb","wfd","bt"],
         "caps":{"opus":true,"pcm":true,"aec":true,"agc":true,"ns":true}}
S -> C  {"t":"challenge","nonce":"<base64, 16 случайных байт>"}
C -> S  {"t":"auth","mac":"<base64, 32 байта HMAC>"}
S -> C  {"t":"ok","session":"<uuid>","media_port":47822,"media_mode":"udp|tcp",
         "cert_fp":"<hex sha256>","media_salt":"<base64, 32 случайных байта>",
         "jitter":{"min_ms":20,"target_ms":40,"max_ms":120}}
   или  {"t":"err","code":"bad_token|wrong_proto|busy|invalid_state|internal","msg":"..."}
```

Вычисление `mac`: `HMAC_SHA256(token_raw_32B, nonce_raw_16B || "phonemic-auth-v1")`, результат base64.
`token_raw_32B` — сырые 32 байта токена (см. §9.1).

После `err` сервер закрывает соединение. Код `busy` — на ПК уже активная сессия.

### 5.2 Управление потоком

```
C -> S  {"t":"start_stream","codec":"opus|pcm","frame_ms":10|20,
         "bitrate_kbps":48000,"mode":"voice|music",
         "aec":true,"agc":false,"ns":true,"gain":1.0}
S -> C  {"t":"stream_started","media_mode":"udp|tcp"}
C -> S  {"t":"cmd","cmd":"set_volume","value":0.8}          // 0.0 .. 1.5, 1.0 = 0 dB
C -> S  {"t":"cmd","cmd":"set_mute","value":true}           // мьют НА ТЕЛЕФОНЕ
C -> S  {"t":"cmd","cmd":"stop_stream"}
C -> S  {"t":"ping","id":123,"ts_client":1690000000123}     // каждые 1000 мс
S -> C  {"t":"pong","id":123,"ts_client":1690000000123,"ts_server":1690000000141}
C -> S  {"t":"bye","reason":"user_stop"}
```

### 5.3 Телеметрия и события

```
S -> C  {"t":"stats","rtt_ms":12,"buffer_ms":40,"pkt_total":1523,"pkt_lost":3,
         "underruns":0,"driver_ok":true}
S -> C  {"t":"event","code":"stream_stopped|driver_missing|driver_error|media_timeout|...","msg":"..."}
```

Телефон тоже отправляет `stats` (не чаще 1 раза в 2 с):
```json
{"t":"stats","battery_pct":87,"pkt_total":1523,"pkt_lost":0,"buffer_ms":20}
```

Оба поля `pkt_total`/`pkt_lost` — счётчики с момента старта потока. `rtt_ms` считает ПК по ping/pong. `driver_ok=false`, если IOCTL-устройство драйвера не найдено.

## 6. Медиа-пакет (единый формат для UDP, TCP и RFCOMM)

Заголовок — 16 байт, все числа **big-endian**:

| Смещение | Размер | Поле | Описание |
|---|---|---|---|
| 0 | 2 | `magic` | `0x504D` |
| 2 | 1 | `version` | `1` |
| 3 | 1 | `flags` | bit0 `0x01` = зашифрован (всегда 1), bit1 `0x02` = muted (отправитель в мьюте), bit2 `0x04` = end-of-stream |
| 4 | 4 | `seq` | номер пакета, начиная с 1 |
| 8 | 4 | `ts` | позиция первого сэмаpayload в сэмплах @48 кГц, с начала потока |
| 12 | 1 | `ptype` | `1` = Opus, `2` = PCM16 |
| 13 | 1 | `reserved` | 0 |
| 14 | 2 | `plen` | длина полезной нагрузки **после заголовка** (включая counter+tag при шифровании) |

Затем полезная нагрузка:

- **Нешифрованный** (не используется в v1, зарезервировано): `payload[plen]`.
- **Зашифрованный** (обычный случай): `counter (8B, big-endian)` + `ciphertext` + `tag GCM (16B)`.
  Итоговый `plen = 8 + len(ciphertext) + 16`.

### 6.1 Передача по разным медиа-каналам

- **UDP**: один пакет = одна датаграмма (заголовок + payload). Размер ≤ 1500 байт вместе с IP/UDP-заголовками — следить за битрейтом Opus.
- **TCP / RFCOMM**: пакеты идут потоком подряд, разделение — по заголовку (`plen`).
  Читатель обязан читать ровно 16 байт заголовка, затем ровно `plen` байт payload.

### 6.2 Кодеки

| `ptype` | Формат кадра | Размеры |
|---|---|---|
| `1` (Opus) | один Opus-кадр, 48000 Hz mono | 10 или 20 мс (типично 20 мс из MediaCodec) |
| `2` (PCM16) | PCM 16-bit LE mono 48 кГц | ровно 10 мс = 960 сэмплов = 1920 байт |

**Важно про Opus**: CSD (OpusHead) по сети не передаётся. Декодер на ПК обязан:
1. Инициализировать `OpusDecoder(48000, 1)`.
2. Отбросить первые **312 сэмплов** (стандартный preskip) после старта потока.
3. При потере пакета вызывать PLC (`Decode(null, 0, 0, ...)` в Concentus).

## 7. Задержка (буферы дрожания)

Пресеты на стороне ПК (min / target / max, мс):

| Пресет | min | target | max |
|---|---|---|---|
| Ультра | 10 | 30 | 100 |
| Баланс (по умолчанию) | 20 | 40 | 120 |
| Стабильный | 40 | 80 | 250 |

Адаптация: при недоборе данных (+underrun) целевой буфер растёт на 10 мс; при 5 с без потерь — уменьшается на 5 мс; зажат в [min, max]. Оценка суммарной задержки: захват (10) + сеть (~1-3) + джиттер-буфер + декодирование (кадр) + драйвер (~10-20). «Ультра» + PCM ≈ 35-45 мс, «Баланс» + Opus ≈ 70-90 мс.

## 8. Криптография

### 8.1 Токен
- 32 случайных байта, представление — base64url **без padding** (43 символа).
- Генерируется на ПК при первом запуске; вводится/вставляется на телефоне; хранится в EncryptedSharedPreferences (Android) и в `%LOCALAPPDATA%\PhoneMic\settings.json` с ACL только для текущего пользователя (Windows).
- Для вычислений используется **сырой** декодированный base64url 32-байтовый массив.

### 8.2 TLS (control и tcp-медиа)
- TLS 1.2+ (рекомендуется 1.3), сервер предъявляет самоподписанный сертификат.
- Pinning: SHA-256 отпечатка DER-сертификата, hex-lowercase. Клиент сверяет после handshake.
- TCP-медиа использует тот же сертификат и тот же pin.

### 8.3 Ключи медиа (AES-256-GCM)
```
master     = SHA256(token_raw_32B)
media_key  = HKDF-SHA256(master, salt = media_salt (32B из "ok"), info = "phonemic-media-v1")  -> 32B
ctlbt_key  = HKDF-SHA256(master, salt = media_salt,            info = "phonemic-control-bt-v1") -> 32B
nonce_pref = HKDF-SHA256(master, salt = media_salt,            info = "phonemic-nonce-v1")      -> 8B
  nonce_pref[0..3]  — префикс пакетов ТЕЛЕФОН -> ПК
  nonce_pref[4..7]  — префикс пакетов ПК -> ТЕЛЕФОН
nonce      = nonce_pref(4B) || counter(8B, big-endian, начиная с 1, +1 на каждый пакет направления)
```
GCM tag — 16 байт, добавляется в конец ciphertext. AAD не используется (null).
Счётчики — раздельные для каждого направления и каждого канала (медиа / control-bt).
Приёмник отслеживает окно последовательностей (replay-защита, окно 512 пакетов).

### 8.4 Bluetooth control-фрейминг (без TLS)
Поверх RFCOMM `...0B12`: тот же медиа-заголовок (§6), `ptype=3` (JSON-сообщение управления).
- **До получения `ok`** (hello/challenge/auth/ok): `flags.encrypted=0`, payload — открытый UTF-8 JSON. (Сам RFCOMM-канал шифруется на уровне Bluetooth.)
- **После `ok`**: payload шифруется `ctlbt_key` (salt = `media_salt` из `ok`), nonce-счётчик — общий для control-направления, начинает отсчёт после `ok`.
Внутри — те же JSON-сообщения §5.1–5.3.

## 9. Безопасность и приватность

1. **TOFU-pinning**: при первом подключении TLS телефон получает реальный отпечаток предъявленного сертификата; сервер присылает `cert_fp` в `ok`. Если совпадают — пользователь подтверждает в диалоге, отпечаток сохраняется как pin. Все последующие подключения: TrustManager принимает сертификат только с совпавшим отпечатком, иначе — разрыв с ошибкой «отпечаток изменился».
2. Windows-приложение обязано: хранить настройки с приватным ACL, не логировать токен, показывать токен только по кнопке «Показать».
3. Контроль входящих правил брандмауэра: при первом запуске ПК-приложение предлагает добавить правила для `CONTROL_PORT`/`MEDIA_PORT` (TCP/UDP) — см. `FirewallService`.
4. Приватность микрофона Windows (Параметры → Конфиденциальность → Микрофон) действует стандартно: драйвер — обычное аудиоустройство.

## 10. Коды ошибок `err`

| Код | Значение |
|---|---|
| `bad_token` | HMAC не совпал |
| `wrong_proto` | `proto != 1` |
| `busy` | уже есть активная сессия |
| `invalid_state` | команда в неправильном состоянии |
| `internal` | прочее |

## 11. Поведение при сбоях

- Разрыв control-канала: клиент переподключается с экспоненциальной задержкой 1→8 с (макс. 8), возобновляет поток после `ok`.
- UDP: потери скрывает декодер (PLC/повтор); 3 с без пакетов — ПК шлёт `event: media_timeout` и подаёт тишину в драйвер.
- Переключение транспорта: только через `stop_stream`/`bye` и новое подключение (v1).
